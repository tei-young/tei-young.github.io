소개 · 지원 동기

3년 7개월 동안 QA Engineer로 일하면서, 기능이 명세대로 동작하는 것과 사용자가 실제로 그 기능을 쓰는 것은 다르다는 걸 계속 확인했습니다. 커머스 회사에서는 전체 인기 상품을 추천하자는 기획에, 평소 관심 있거나 자주 사는 카테고리의 상위 상품이 더 매력적일 것이라는 가설로 '자주 구매하는 카테고리의 인기 상품'을 제안했습니다. A/B 테스트에서 클릭률이 10% 미만에서 18% 이상으로 올라 제안안으로 출시됐고, 같은 상품이라도 나에게 맞춰져 있을 때 더 많이 눌린다는 걸 그때 숫자로 확인했습니다.

Vesta는 회사에 다니면서 이미 만들기 시작한 서비스입니다. 지인 원장님에게 "기존 앱은 너무 어렵다, 간단하게 입력만 해서 예약·매출·고객을 다 관리하고 싶다"는 말을 듣고, 이렇게 들어가면 큰 시장은 아니어도 정말 필요한 원장님들에게는 닿을 수 있겠다고 생각했습니다. 사이드 프로젝트로 시작해 개인사업자로 전환했고, 만들면서 제 설계 의도와 사용자의 실제 행동이 다를 때 어느 쪽을 따라야 하는지를 가장 많이 고민했습니다.

혼자 만드는 일은 재미있지만 무엇을 무료로 두고 어디서 돈을 받을지, 어느 채널에 시간을 쓸지 같은 사업적인 판단은 매번 작은 근거로 내려야 했고, 그 부분이 가장 부족하다고 느꼈습니다. 하나의 카테고리를 사업처럼 처음부터 끝까지 맡으면서 그 판단을 더 많은 고객과 데이터 위에서 배우고 싶습니다.

대신 바로 보탤 수 있는 경험도 있습니다. 고객을 직접 만나 문제를 정의하고, 3~5일 주기로 기획부터 출시까지 혼자 돌려 본 경험은 가설을 빠르게 고객 앞에 내놓아야 하는 Problem Solver의 일과 같은 방식입니다. 커머스에서는 주문·결제·배송 흐름을 사용자 관점에서 검증했고 추천 기획에 개인화 대안을 내 A/B로 확인해 봤습니다. 또 AI가 만든 결과물을 판정 기준을 세워 검증한 뒤 실무에 써 왔기 때문에, 쇼핑 AI 에이전트가 내놓는 추천과 답이 고객에게 믿을 만한지 확인하는 일에서도 이 경험을 살릴 수 있다고 생각합니다.

문제를 현장에서 정의합니다

지인 원장님의 불편에서 시작했고, 출시 후에도 매장을 직접 찾아가 왜 쓰는지, 왜 안 쓰는지를 듣습니다.

원장님들이 이미 쓰던 도구에서 가설을 찾고, 3주 만에 내놓아 확인하다

10명 복귀출시 푸시 1회로 휴면·기존 유저가 돌아와 링크 생성

가입자는 87명이 되었지만 주간 활성은 21명이었습니다. 설치만 해두고 쓰지 않는 원장님들을 다시 데려와야 했고, 새로운 원장님이 들어올 길도 필요했습니다. 그래서 새 기능을 고민하기 전에 원장님들이 지금 무엇을 쓰고 있는지부터 살펴봤습니다.

  • 그런데 이 링크들은 '내 예약 서비스'와 거의 연결되어 있지 않았습니다. 네이버 예약처럼 손님이 예약을 요청하고 원장님이 수락·거절하는 흐름이 링크 안에서 이어지지 않았습니다.

손님에게 보이는 화면이라 완성도를 먼저 챙기기
  • 디자이너 지인과 실제 원장님들께 사용 경험과 디자인 방향을 계속 자문받다 보니 기획부터 출시까지 테스트를 포함해 3주가 걸렸고, 지금까지 만든 기능 중 가장 긴 기간이었습니다.
  • 출시 직전에는 템플릿 방식(CASE 02)과 함께 구독 구조를 더했습니다. 이미지를 많이 쓰는 페이지라 구현한 코드 기준으로 서버비를 계산해 보니 방문자가 늘수록 제 부담이 커지는 구조였고, 그래서 이미지를 일정 개수 이상 쓰거나 컬러를 더 다양하게 고르려면 구독하도록 바꿨습니다.
출시하고, 누가 돌아오는지 확인하기
  • 출시일에 앱을 설치한 전체 사용자에게 푸시를 한 번 보냈고, 기존 사용자와 한 달 이상 접속하지 않았던 휴면 사용자 10명이 돌아와 베스타 링크를 만들었습니다(GA4 이벤트로 확인).
  • 앱 진입 시 링크 제작을 안내하는 팝업은 이미 링크를 가진 사용자가 많아 전환이 낮게 나오는 것으로 보고 있습니다. 링크를 거친 예약과 알림톡 사용량은 이제 집계를 시작한 단계라, 가설의 나머지는 이 두 숫자로 확인할 예정입니다.

CASE 02Vesta · 템플릿 · 진입점

내 설계 방향보다 사용자의 속도를 택하다

90%+베스타 링크 빌드 진입 후 게시 완료

Vesta는 '하나하나 내 맞춤으로 설정해 두면, 나중에는 조금만 조작해도 다 관리되는 앱'을 목표로 만들었습니다. 그런데 사용자가 원하는 게 처음부터 많이 설정하는 것보다 지금 당장 빨리 끝내는 것일 때가 있었고, 그럴 때는 제 설계 방향보다 사용자의 속도를 따랐습니다.

선택지를 줄여서 빠르게 — 베스타 링크 템플릿
  • 출시 전 일부 원장님들께 클로즈 베타처럼 베스타 링크 빌드를 먼저 써보게 했습니다. 저는 Vesta 전체의 방향대로 항목 하나하나를 직접 설정하도록 유도했는데, "대충 만들어져 있는 템플릿을 그대로 쓰고 싶다"는 피드백이 나왔습니다.
  • 제 방향과는 달랐지만, 원장님들이 원한 건 링크를 빨리 만들어 거는 것이었습니다. 그래서 대표 템플릿 2종 중 하나를 고르고 색상·버튼·이미지만 바꾸는 방식으로 선택의 폭을 오히려 줄였고, 지금은 빌드에 진입한 원장님의 90% 이상이 게시까지 완료합니다.
익숙한 자리로 옮기기 — 간편입력 진입점
  • 간편입력은 문장 한 줄로 예약을 만드는 핵심 기능입니다. 처음에는 Claude나 ChatGPT처럼 일별 시트 하단에 입력창을 항상 띄워 두었는데, 입력창이 눈에 잘 안 띈다는 피드백이 많았습니다.
  • 원장님들에게 익숙한 건 채팅 입력창보다 캘린더 앱의 + 버튼이었기 때문에, 여러 캘린더 서비스처럼 + 버튼을 누르면 입력창이 나오도록 바꿨습니다.
덜 쓰게 하고 싶은 경로는 깊게 — 직접입력 2depth
  • 반대로 항목을 하나씩 고르는 직접입력은 + 버튼 다음에 [직접 선택해서 입력]을 한 번 더 눌러야 하는 2depth로 내렸습니다.
  • 간편입력이 더 빠르고, 파싱에 실패해도 입력한 내용이 상세입력으로 넘어가기 때문에 손해가 없다는 걸 사용자가 자연스럽게 익히도록 의도한 구조입니다.
피드백을 받으면 서비스의 정체성을 바꾸는 요청인지, 같은 일을 더 빨리 끝내게 해주는 요청인지부터 나눠 봤습니다. 템플릿과 + 버튼은 뒤의 경우라서 제 설계를 바꿨고, 앞의 경우는 CASE 06처럼 반영하지 않았습니다.
결과
  • 템플릿 방식 도입 후 베스타 링크 빌드 진입 대비 90% 이상 게시 완료
  • 간편입력을 기본 경로로, 직접입력을 보조 경로로 재배치해 핵심 기능이 먼저 보이도록 개편
CASE 03Vesta · 간편입력

핵심 기능을 원장님이 실제로 일하는 방식에 맞춰 넓히다

3단계 확장단건 → 복수 예약 → 카카오톡 메시지 붙여넣기

간편입력의 첫 버전은 "김민지 3시 눈썹문신" 같은 한 건의 예약만 이해했습니다. 그런데 원장님들의 예약은 한 건씩 깔끔하게 들어오지 않습니다. 여러 건을 한 번에 적어야 할 때도 있고, 이미 카카오톡으로 손님에게 보낸 예약 메시지가 있기도 합니다. 그래서 원장님이 이미 가지고 있는 텍스트를 그대로 넣을 수 있게 입력 형태를 넓혔습니다.

적자의 상한을 먼저 계산하기

CASE 07애즈위메이크 · QA Engineer2025.09 ~ 2026.07 · 커머스 B2C·B2B

커머스 사용자의 행동을 기준으로 기획과 정책을 바꾸다

마트 상품 비대면 배송 서비스(B2C)와 마트 사장님용 상품관리 솔루션(B2B)을 QA로 담당했습니다. 검증하는 역할이었지만, 사용자가 실제로 어떻게 사고 어떻게 다시 시도하는지를 기준으로 기획과 정책에도 의견을 냈습니다.

추천 기획에 대안을 가설로 내기
  • 상품 추천 기능이 '전체 인기 상품'을 보여주는 방향으로 킥오프되었습니다. 전체 인기 상품도 충분히 매력적이지만, 저는 평소 관심 있거나 자주 사는 카테고리의 상위 상품이 더 매력적일 것이라고 생각했습니다. 나에게 맞춰진 상품일수록 더 많이 누르고 살 것이라는 개인화에 대한 가설이었습니다.
  • 확신할 근거가 있는 건 아니었기 때문에 주장 대신 A/B 테스트를 제안했고, 클릭률 이벤트를 기준으로 2주간 비교했습니다.

How I Build

AI에게 구현을 맡기고, 판단과 검증을 맡다

Vesta의 코드는 Claude Code로 작성합니다. 저는 무엇을 왜 만들지, 로직과 정책이 맞는지, 화면이 원장님에게 자연스러운지, 비용과 BM에 맞는지를 판단하는 데 시간을 씁니다. 기능 단위로 3~5일 주기로 기획부터 스토어 출시까지 반복합니다.
